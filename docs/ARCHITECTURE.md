# Подробности реализации

Справочник по устройству сервиса. Краткое описание, запуск и API — в [README](../README.md).

## Архитектура приложения

Слои и направление зависимостей:

```text
┌──────────────────────────────────────────────────────────────────┐
│ api/          HTTP: роуты, зависимости, коды ошибок              │
│ workers/      фоновый worker arq: обработка вебхуков             │
└──────────────────────────────────────────────────────────────────┘
                                  │ вызывают
                                  ▼
┌──────────────────────────────────────────────────────────────────┐
│ services/     сценарии: ассистент, кеш, запись, вебхуки, промпты │
└──────────────────────────────────────────────────────────────────┘
                                  │ вызывают
                                  ▼
┌──────────────────────────────────────────────────────────────────┐
│ domain/       чистая логика и порты: поиск, проверки ответа      │
└──────────────────────────────────────────────────────────────────┘
                                  ▲
                                  │ реализуют порты
┌──────────────────────────────────────────────────────────────────┐
│ integrations/ адаптеры: RAG, Groq, Redis, arq, CRM-заглушка      │
│ db/           адаптеры: сессия, модели, репозитории Postgres     │
└──────────────────────────────────────────────────────────────────┘
```

`bootstrap.py` — корень композиции: единственное место, где адаптеры подставляются вместо портов.

### Куда класть новый код

- **Порт** — `app/domain/ports/<агрегат>.py` (`assistant`, `suggestions`, `conversations`, `webhooks`, `quotas`,
  `llm_health`); импортируется из пакета: `from app.domain.ports import Assistant`.
- **Реализация с БД** — `app/db/repositories/<тот же агрегат>.py`; **внешняя система** — `app/integrations/<система>/`
  (Redis, Groq, arq, CRM, RAG). Состояние модели (`LlmHealth`) тоже адаптер: `integrations/llm/health.py`.
- **Сценарий** — `app/services/`: работает только через порты, не импортирует адаптеры, SQLAlchemy и Redis. Адаптер
  подставляется в `bootstrap.py`. Когда файлов в `services/` станет 15+, группируйте по фиче (диалоги, квоты и учёт), а не
  по слою.
- **Чистые правила без ввода-вывода** — `app/domain/` (проверки ответа, поиск, статусы диалога).
- Сознательное послабление: домен использует pydantic-модели из `app/schemas/` (`AnalyzeRequest`, `AnalyzeResponse`) как
  общие типы.

Границы проверяет import-linter: контракты в `[tool.importlinter]` в `pyproject.toml`, запуск `uv run lint-imports`, тот же
прогон входит в `pytest` (`tests/test_architecture.py`). Домен не импортирует БД, сервисы, адаптеры, API и инфраструктурные
библиотеки; сервисы не импортируют адаптеры; адаптеры не импортируют сервисы и API.

Цепочка ассистента собрана декораторами одного интерфейса `Assistant`:

```text
метрики → запись подсказки → кеш → дневной бюджет → ядро (AssistantService)
```

Ядро не знает ни о кеше, ни о БД, ни о лимитах. Запись стоит снаружи кеша, поэтому подсказка из кеша тоже
сохраняется и получает идентификатор для оценки менеджером. Бюджет стоит под кешем, поэтому ответы из кеша его не тратят.

## Как строится ответ

**Как строится ответ.** Обращение делится на подвопросы («сколько стоит и есть ли доставка» ищутся отдельно, а
результаты чередуются, чтобы узкий вопрос не потерялся), найденные записи вместе с историей диалога уходят в модель
(Groq, строгая JSON-схема). Первым полем схемы идёт `analysis` — короткое рассуждение по шагам (цепочка рассуждений),
и только затем ответ и подсказка. Промпты лежат в [prompts/](../prompts/) и версионируются (текущая версия — `v2`, задаётся `PROMPT_VERSION`; версия
записывается в каждую подсказку и входит в ключ кеша).

**Стиль общения (промпт `v2`).** Ответ клиенту пишется как сообщение живого человека в мессенджере, а не как
справка: сразу по вопросу, 1–4 коротких предложения, без пересказа лишних деталей (шифрование платежей, 3D Secure) и
без шаблонного «Чем ещё могу помочь?». Ассистент опирается на уже сказанное в диалоге, не здоровается повторно и не
говорит клиенту служебных слов («база знаний», «запись»). Про **промокод**: цена по промокоду хранится отдельным полем
записи, подаётся модели отдельной строкой и разрешена к упоминанию один раз за диалог и только при вопросе о цене или
скидках; промокод, скидки и бонусные баллы не считаются допродажей. Сравнения («что дешевле») строятся по автоматическим
сводкам цен, которые пересчитываются из цен самих товаров.

**Защита от ошибок (проверяется кодом, а не только промптом):**

- клиентский текст и история передаются в тегах как данные, команды внутри них игнорируются (prompt injection);
- если в базе нет ничего по теме, модель получает пустой контекст и вместо выдумки отвечает «уточню» с эскалацией;
- числа из трёх и более цифр в ответе сверяются с найденными записями и диалогом, расхождения попадают в `warnings`;
- оценочные слова («выгоднее», «самый», «лучший», «популярный»), которых нет в данных, тоже попадают в `warnings`;
- по темам здоровья к ответу добавляется оговорка про врача (если она уместна и модель её не написала);
- темы повышенного риска (беременность, кормление, дети, лекарства, хронические болезни): наборы под состояния
  скрываются от модели, а подсказка по допродаже заменяется стандартной («сейчас не уместна»).

## Как устроен поиск

- Запись базы знаний — один узел LlamaIndex: заголовок, ответ и ключевые слова; метаданные в эмбеддинг не попадают.
- Два ретривера — векторный (косинусная близость) и полнотекстовый Postgres — объединяются методом Reciprocal Rank
  Fusion. Собственная реализация понадобилась, потому что гибридный режим `PGVectorStore` просто склеивает выдачи с
  оценками в разных шкалах.
- Порог релевантности (`RAG_MIN_DENSE_SCORE`, по умолчанию 0,81) отсекает обращения не по теме. Он подобран на
  небольшой выборке запросов и будет перепроверен на эталонных диалогах.
- Индексация идемпотентна: таблица `kb_documents` хранит хеш каждой записи, повторный запуск ничего не пересчитывает.

## Кеш ответов

Повторяющиеся вопросы не должны тратить запросы к Groq (лимиты бесплатного тарифа, токены, задержка), поэтому готовые
ответы кешируются в Redis (`CachingAssistant`, TTL `CACHE_TTL_SECONDS`, по умолчанию час):

- **Ключ** строится по смыслу запроса: режим, нормализованное сообщение (без регистра, лишних пробелов и знаков в
  конце: «Сколько стоит?» и «сколько  стоит» — один ключ), **последние 2 реплики** диалога (`CACHE_HISTORY_TURNS`) и
  отпечаток более ранней истории, если она есть. Отпечаток нужен, потому что модель видит до 20 реплик: без него ответ,
  полученный в контексте одного клиента (в том числе с подсунутой в ранних репликах инструкцией), достался бы другому
  клиенту с теми же двумя последними репликами. Цена: в длинных диалогах кеш срабатывает только на точный повтор всей
  истории, а спам одним вопросом в растущем диалоге кеш не собирает; от него защищают лимиты ниже.
  Идентификатор сделки в ключ не входит: ответ на один вопрос от сделки не зависит.
- **Версия окружения** (`промпты : модель : версия базы знаний`) входит в ключ: после смены промпта, модели или
  переиндексации базы старые ответы автоматически перестают использоваться.
- **Одновременные одинаковые запросы** сливаются в один вызов модели: пять параллельных копий дают один `miss` и четыре
  `hit`.
- Ответ из кеша возвращается с `cache_status: "hit"`, нулевым расходом токенов и записывается в `suggestions`
  (`cache_hit = true`), поэтому каждая выданная менеджеру подсказка получает свой `suggestion_id`.
- Ошибки модели не кешируются. Недоступность Redis не ломает запрос: кеш деградирует в «промах».

## Лимиты, метрики и обратная связь

**Лимиты** (счётчики в Redis; при недоступности Redis запрос не блокируется, а причина пишется в лог):

- на клиента: `CLIENT_RATE_LIMIT_PER_MINUTE` (по умолчанию 20) обращений в минуту на сделку (`lead_id`) и втрое больше
  на IP-адрес, чтобы спамера с подставными `lead_id` тоже остановить; ответ `429` с `Retry-After`;
- публичный чат, по IP-адресу: `CLIENT_NEW_CONVERSATIONS_PER_HOUR` (10) новых диалогов в час и
  `CLIENT_DAILY_MESSAGES_PER_IP` (60) сообщений в сутки (считается и первое сообщение диалога). Каждое сообщение может
  стоить запроса к модели, а бюджет общий: без этих лимитов один адрес выбрал бы его у остальных клиентов, а пустые
  диалоги вытеснили бы настоящие из списка входящих;
- IP берётся из соединения. За обратным прокси укажите его адрес в `FORWARDED_ALLOW_IPS` (uvicorn тогда читает
  `X-Forwarded-For`); значение `*` не ставьте, иначе подставной заголовок обойдёт лимиты;
- дневной бюджет обращений к модели: `DAILY_REQUEST_LIMIT` (по умолчанию 150, сутки по UTC). Он стоит под кешем,
  поэтому ответы из кеша бюджет не тратят; при исчерпании `429`. Вебхук в этом случае worker не теряет: он откладывает повтор до освобождения бюджета (до `WEBHOOK_MAX_TRIES` попыток), затем событие получает статус `failed`. Тайм-аут задачи worker'а (300 с) перекрывает худший случай вызова модели (моделей × 2 попытки × 45 с).

**Метрики Prometheus** — `GET /metrics` у API (порт 8000, нужен заголовок `X-Manager-Token`) и у worker'а (порт 9101,
без токена), оба опубликованы только на localhost:

| Метрика | Что показывает |
|---|---|
| `assistant_requests_total{mode,cache,outcome}` | обращения по режиму, попаданию в кеш и исходу (`ok`, `llm_unavailable`, `rate_limited`) |
| `assistant_latency_seconds{cache}` | гистограмма времени подготовки подсказки |
| `llm_tokens_total{direction,model}` | токены, потраченные на вызовы модели |
| `rate_limited_total{scope}` | отказы по лимитам (`client`, `daily`) |
| `webhook_events_total{result}` | вебхуки: `accepted`, `duplicate`, `processed`, `retry`, `failed`, `queue_unavailable` |
| `feedback_total{rating}` | оценки менеджеров |

**`GET /api/stats`** — сводка за сутки (UTC) из БД: подсказки, доля кеша, токены, средние задержки, оценки. Средняя
задержка «из кеша» включает ожидание запросов, слитых с уже идущим, поэтому может быть заметно больше миллисекунд.

**Обратная связь.** `POST /api/feedback` принимает `suggestion_id` (из ответа `/api/analyze`), `rating` (`1` или `-1`),
необязательные `comment` и `manager_id`. Повторная оценка того же менеджера обновляет предыдущую, несуществующая
подсказка даёт `404`. Разбор оценок для правки промптов и базы знаний:

```bash
python -m scripts.feedback_report --limit 20
```

Скрипт печатает сводку по версиям промпта и моделям и последние негативные оценки вместе с вопросом клиента, ответом,
подсказкой, использованными источниками и комментарием менеджера. Дальше цикл такой: разобрать негативные случаи,
поправить промпт (новая версия в `prompts/`) или запись базы (`data/knowledge_base.json`), переиндексировать и сравнить
доли негативных оценок по версиям.

## Справочник ссылок для ассистента

`data/site_links.json` — единственный список страниц сайта, кроме страниц найденных записей, на которые ассистент может дать кнопку-ссылку
(оплата и доставка, каталог, контакты, сертификаты, инструкции, о компании, опт, партнёры). У записи есть `title`, `url` (только
`https://o-complex.com/…`) и `keywords`: если ключевое слово встретилось в сообщении клиента, под ответом появляется кнопка.
Остальные ссылки, которые модель напишет сама, вырезаются из ответа. Чтобы добавить страницу, допишите запись в файл и пересоберите
образ: `docker compose up -d --build api worker`.

## Эндпоинты

| Метод и путь | Кто | Назначение |
|---|---|---|
| `POST /api/chat/conversations` | клиент | начать диалог (с первым сообщением или без); возвращает токен |
| `GET /api/chat/conversations/{token}` | клиент | диалог с историей |
| `GET /api/chat/conversations/{token}/messages?after=` | клиент | только новые сообщения |
| `POST /api/chat/conversations/{token}/messages` | клиент | сообщение клиента; подсказка для менеджера готовится в фоне |
| `POST /api/chat/conversations/{token}/contact-request` | клиент | запрос на связь: способ, контакт, время, комментарий |
| `GET /api/manager/conversations?status=&q=&limit=` | менеджер | входящие со счётчиками по статусам; по умолчанию 100 диалогов, `has_more` показывает, что есть ещё (`limit` до 500) |
| `GET /api/manager/conversations/{id}` | менеджер | переписка, карточка клиента, заметка, подсказка ИИ (диалог отмечается прочитанным) |
| `POST /api/manager/conversations/{id}/messages` | менеджер | ответ клиенту (можно с `suggestion_id`) |
| `POST /api/manager/conversations/{id}/status` | менеджер | сменить статус |
| `PUT /api/manager/conversations/{id}/note` | менеджер | внутренняя заметка |
| `POST /api/manager/conversations/{id}/suggestion` | менеджер | заново подготовить подсказку |
| `GET /api/manager/session` | менеджер | проверка кода доступа |
| `GET`/`PUT /api/manager/away` | менеджер | режим «менеджер ушёл» (ассистент отвечает сам) |
| `GET /api/manager/model-status` | менеджер | какая модель подключена и работает ли она |
| `PUT /api/manager/model` | менеджер | выбрать модель, которая отвечает первой (`null` — автоматический порядок) |
| `GET /api/demo/config` | все | включён ли демо-режим |
| `POST /api/demo/manager-session` | все, только при `DEMO_MODE=true` | выдаёт код менеджера для автоматического входа консоли |
| `POST /api/analyze`, `POST /api/feedback`, `GET /api/stats`, `GET /metrics` | менеджер | подсказка ИИ, оценка, статистика за сутки, метрики |
| `POST /webhook/amocrm` | AmoCRM (`X-Webhook-Secret`) | событие «новое сообщение клиента» |

Статусы: клиент пишет — `new` (закрытый диалог открывается заново), менеджер открывает — `in_progress`, отвечает — `waiting_client`, клиент просит связаться — `callback` (остаётся, пока менеджер не сменит вручную), `closed`. Новый статус вычисляется в БД под блокировкой строки диалога, поэтому параллельные сообщение клиента и смена статуса менеджером не затирают друг друга. Запрос связи (контакт, системное сообщение, статус) сохраняется одной транзакцией; сбой CRM его не откатывает. Лимиты: 20 сообщений в минуту на диалог и 60 на IP, плюс лимиты новых диалогов и суточных сообщений (см. выше). Переписка в консоли и в ответе клиенту ограничена последними 300 сообщениями.

## Веб-интерфейс

Оформление в палитре o-complex.com (молочный фон, тёмные кнопки, лаймовый акцент), светлая и тёмная темы. Статические файлы лежат в [app/static/](../app/static/), без сборки; тексты выводятся только через `textContent`.

**Шрифт.** На устройствах Apple — родной SF Pro, на остальных системах — самохостинговый **Inter** (близкий к SF, лицензия OFL, [app/static/fonts/](../app/static/fonts/)): три подмножества (кириллица, латиница, латиница расширенная со знаком ₽), предзагрузка, кеш на год. Символы нарисованы SVG-иконками, чтобы запасные шрифты не сдвигали строки.

### Экран клиента — `http://127.0.0.1:8000/`

Публичный чат с менеджером. **Подсказок ИИ клиент не видит**: их нет ни на странице, ни в ответах его API.

- диалог создаётся с первым сообщением, токен хранится в браузере (после перезагрузки клиент возвращается в свой чат);
- быстрые вопросы, время и отметка доставки, счётчик символов, обновление раз в 2,5 с, счётчик новых сообщений во вкладке;
- кнопка **«Новый чат»**: если в диалоге уже есть переписка, сначала спрашивает подтверждение, затем сбрасывает токен в браузере и открывает пустой чат; прежний диалог остаётся у менеджера во входящих;
- **«Связаться с менеджером»**: форма с выбором способа связи (телефон, Telegram, WhatsApp, email или ответ в этом чате), контактом, удобным временем и комментарием; контакт проверяется на формат и уходит только в карточку клиента у менеджера;
- способы связи компании (телефоны, почта, адрес, ссылка на страницу контактов сайта) рядом с чатом.

### Демо-переключатель экранов

Для записи видео и показа в одном окне включите `DEMO_MODE=true` в `.env`. Внизу обеих страниц появится панель **«Демо: Клиент | Менеджер»** (обычные ссылки, горячие клавиши `Alt+1` и `Alt+2`, на Mac `⌥1` и `⌥2`):

- консоль менеджера **входит сама** (без ввода кода) и сразу открывает диалог: последний открытый или самый важный (новые и просящие связаться выше);
- клиентский чат хранится в браузере, поэтому при возврате на экран клиента переписка на месте;
- после «Выйти» автовход отключается до нажатия «Войти как демо-менеджер».

В настройках режим по умолчанию **выключен** (`DEMO_MODE=false`), а в `.env.example` **включён**: экрана входа в консоль нет намеренно, и без демо-режима она не получает код доступа. Включённый режим отдаёт код менеджера без ввода любому, кто открыл страницу, поэтому подходит только для локальной демонстрации.

### Консоль менеджера — `http://127.0.0.1:8000/manager`

- **Входящие**: диалоги со статусами (`Новый`, `В работе`, `Ждём клиента`, `Просит связаться`, `Закрыт`), фильтр по статусу со счётчиками, поиск по имени и тексту, счётчик непрочитанных, уведомление о новом сообщении; горячие клавиши консоли: `⌘K` (на других ОС `Ctrl+K`) — поиск, `⌥↑` / `⌥↓` — предыдущий и следующий диалог, `⌘Enter` (`Ctrl+Enter`) — отправить подсказку; горячие клиенты (со звездой), затем новые и просящие связаться всегда выше остальных.
- **Переписка**: полная история, разделители дней, пометка у ответов «по подсказке ИИ» / «по подсказке ИИ, с правками», смена статуса, ручной ответ.
- **Карточка клиента**: имя, канал, начало диалога, число сообщений; для запроса связи выделенный блок с способом, контактом (кнопки «копировать» и ссылка `tel:`/`t.me`/`wa.me`/`mailto:`), удобным временем и комментарием; внутренняя заметка менеджера, клиенту она не видна.
- **Подсказка ИИ** к последнему сообщению клиента (готовится сама, как только клиент написал): ответ клиенту можно править и отправить одной кнопкой (`Ctrl+Enter`), подсказка по допродаже, предупреждения проверок, источники со шкалой схожести и ссылками на сайт, оценка 👍/👎 с быстрыми причинами, «Сравнить без базы знаний», «Обновить подсказку».
- на узких экранах список и переписка переключаются, горизонтальной прокрутки нет.

**Как это связано с ИИ.** Сообщение клиента сохраняется, в фоне готовится подсказка (состояние `pending → ready/failed` хранится у сообщения), менеджер видит её и решает: отправить как есть, поправить или ответить сам. Признак правки сохраняется, по доле неизменённых подсказок видно, насколько они полезны.

**Приватность.** Контакты клиента не попадают в переписку, в заметку CRM и в запросы к модели; в модель уходят только тексты сообщений клиента и менеджера. Сообщения — вымышленные в демо, реальные данные на бесплатном Groq отправлять не стоит.
